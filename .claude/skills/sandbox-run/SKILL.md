# 概要

- このルールがメンションされた場合は、検証・実験タスク（EDA、データ取得、グラフ可視化、設計の相談等）が依頼されています。
- あなたは依頼されたタスクを達成するまで実行を続けてください。

# 実行フロー

## 共通ルール

- タスクを達成するために必要なコードは適切なプロジェクトの `sandbox/` に書いてください。
- タスク毎にフォルダ分けしてください。
- `YYYYMMDD` はそのアクションを実行した JST 時刻を取得してください。
  - `TZ=Asia/Tokyo date '+%Y%m%d'` のようにコマンドから取得

## 1. 初期化

### 1.0 開発者名の特定

1. `git config user.name` で名前を取得
2. `exp/` 配下のフォルダ名と照合し、最も一致するものを選択
   - 例: `git config user.name` → `shunyooo` → `exp/shunyo` にマッチ
3. 一致するフォルダがない場合はユーザーに確認

### 1.1 プロジェクトの選択・作成

1. **既存プロジェクトを確認**
   - `exp/{開発者名}/project/` 配下のプロジェクト一覧を確認
   - タスクが既存プロジェクトに関連する場合は、そのプロジェクトを選択
   - ただし、プロジェクトの `YYYYMM` から2ヶ月以上経過している場合は、同じテーマでも新規プロジェクトの作成を提案する

2. **新規プロジェクトが必要な場合**
   - ユーザーに新規プロジェクト作成を確認
   - プロジェクト名: `{YYYYMM}_{index}_{プロジェクト名}` 形式
     - `YYYYMM`: プロジェクト開始時期の目安
     - `index`: 2桁の連番（そのYYYYMM内で既存のindex + 1）
     - 例: `202512_05_new_feature_development`
   - プロジェクトディレクトリと `sandbox/` ディレクトリを作成

### 1.2 タスクフォルダの作成

1. タスク用のフォルダを作成します。

- 配置場所: `exp/{開発者名}/project/{YYYYMM}_{index}_{プロジェクト名}/sandbox/`
- フォルダ名は `{YYYYMMDD}-{index}_{タスク名}` としてください。（これをタスクフォルダと呼びます）
- 例: `exp/shunyo/project/202512_01_nanobanana_integration/sandbox/20250527-001_analyze-slot-data`
- index は同日内で連番（001, 002, 003...）

### 1.3 README を作成する

- 作成したフォルダ配下に `000_readme.md` を作成してください。
- これはタスクフォルダのインデックスページです。以下を記述してください：
  - タスク概要（プロジェクト名、背景、目的）
  - 別チャットから参照してもタスクが再開できるような文脈
- このファイルは作業の進行に合わせて **継続的に更新** します：
  - 各レポートの要点を反映
  - 実験結果のサマリーを追記
  - 最終的にはタスク全体のまとめとして機能させる

### 1.4 プロジェクトREADME.mdの更新

タスク作成後、プロジェクトのREADME.md（`exp/{開発者名}/project/README.md`）を更新してください：

- 新しいタスクを該当プロジェクトのsandbox配下に追加
- タスク名の右側に簡潔な説明を記載（30〜50文字程度）
- タスク数も更新（例: `sandbox/ (11 tasks)` → `sandbox/ (12 tasks)`）
- 統計セクションの総タスク数も更新

**フォーマット例**:

```
├── 202512_01_nanobanana_integration/                Google nano banana pro統合
│   └── sandbox/ (9 tasks)
│       ├── ...
│       └── 20251215-001_new_task                            新しいタスクの簡潔な説明
```

## 2. 運用パターン

タスクの性質に応じて2つのパターンを使い分けます。

### パターン A: 自律実行（推奨）

まとまった作業を自律的に任せたい場合。探索的なタスクも含め、計画を立てて自律的に進行する。

**フロー:**

1. `001_plan.md` を作成し、以下を記述：
   - 背景・コンテキスト（なぜこのタスクをやるのか、関連する議論や前提知識）
   - 達成条件
     - 単に「実装した」だけでなく、**それが正しく機能することを検証・評価できた状態**を達成条件とすること
     - 例: 「プロンプトを修正した」ではなく「修正前後で比較実験を行い、改善効果をレポートした」
   - 進め方（ステップバイステップ）
   - **検証・評価方法（具体的に）**: 以下の観点を必ず含めること
     - 評価データの構築方法（どこからデータを取得し、どうラベル付けするか）
     - 比較実験の設計（何と何を比較するか、再現性をどう担保するか）
     - ユーザーへの結果提示方法（HTML レポート、アノテーション UI 等の具体的なフォーマット）
     - 自律的に実行できる範囲と、ユーザー判断が必要なポイントの明確な区別
   - 計画は抽象的な方針ではなく、あなたが自律的に動けるレベルの具体性を持たせること
2. ユーザーにレビューを依頼し、すり合わせ
3. 承認後、**達成条件を満たすまで自律的に実行**（細かい確認は不要）
4. 完了後、レポートを作成し `000_readme.md` を更新

**イテレーション:**
一回の計画で完了しない場合、フィードバックを受けて次の plan を作成する：

```
001_plan.md              # 初期計画 → すり合わせ → 自律実行
002_fetch_data.py
003_report.md
004_plan.md              # フィードバックを受けて次の計画 → すり合わせ → 自律実行
005_analysis.py
006_report.md
...
```

### パターン B: 対話実行

探索的なタスクや、方針を細かく相談しながら進めたい場合。

**フロー:**

1. plan ファイルは不要（または簡易的に作成）
2. ユーザーと対話しながら段階的に進める
3. 必要に応じてレポートを作成

## 3. タスク実行

### 3.1 ファイル命名規則

全てのファイルは連番で管理します：

- `{番号:3桁}_{説明}.{拡張子}`
- 番号は `000` から始まるインクリメント
- レポートも実装ファイルも同じ連番の中で管理

**ファイル構成例:**

```
000_readme.md            # インデックスページ（常に更新）
001_plan.md              # 計画
002_main.py              # 実装
003_report.md            # ステップ1の結果レポート
004_plan.md              # 次の計画
005_analysis.py          # 実装
006_report.md            # ステップ2の結果レポート
```

### 3.2 実装の基本方針

**実装ファイルが必要なケース**:

- データ分析・可視化が必要
- 検証コードの実装
- プロトタイプの作成

**実装ファイルが不要なケース**:

- 調査だけで完結するタスク（既存コードの調査など）
- 設計の相談・レビュー
- データの確認だけ

**実装のポイント**:

- .py ファイルは argparse を使わず、パラメータはファイル内で完結させる
- 各ファイルは独立して実行可能にする
- `src/` 配下の実装済みコードと uv でインストール済みモジュールのみ import 可能

**依存関係とデータ管理**:

- 原則ファイル間の依存関係は作らない
- 中間結果は `data/` フォルダに保存
  - 例: `data/output_002_main.csv`, `data/figure_005_viz.png`
- 必要に応じて以降のファイルで参照可能

### 3.3 レポーティング

- 各ステップの完了時にレポート（`.md`）を連番で作成
- 構成:
  - タスク概要
  - 実行したコマンドや方法（再現性の担保）
  - 結果・考察
  - 生じた問題と解決方法
- レポート作成後、`000_readme.md` に要点を反映

### 3.4 タスクの調整

作業を進める中で、当初の計画を変更する必要が生じた場合:

- 新しい plan ファイルを連番で作成（例: `004_plan.md`）
- ユーザーにレビューを依頼
- 承認後に作業を継続

## 4. タスクの同期（Claude Code の場合）

`000_readme.md` と内部のタスクリストは常に同期するように気をつけてください。

# ルール

1. 依存関係管理

- pip や uv pip コマンドは使用せず、 uv add/uv remove/uv sync を使用すること
- 再現性の問題があるため、uv pip や pip コマンドの実行は避ける
- 直接 pyproject.toml の dependencies を書き換えるのは絶対にやめて、add, remove で更新する

2. 環境構築

- 実行時 uv が参照している環境を使用してください
- 問題が起きた場合は venv を作り直すなどを検討してください
